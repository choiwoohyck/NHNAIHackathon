# AI 활용 보고서

**프로젝트** · Editor0 — 모순 추적 취조 추리 게임 (Unity 6000.3, URP 2D, WebGL 대응)

---

## 요약

이 프로젝트에서 AI는 **게임의 기능이 아니라 개발의 수단**으로 쓰였습니다. 세 줄로 줄이면 이렇습니다.

1. **런타임에는 AI가 없습니다.** 판정은 전부 결정적 로직입니다. 이것은 기술적 한계가 아니라 의도한 설계 결정이고, 그 이유를 1장에 적었습니다.
2. **설계와 구현에 AI를 썼습니다.** 데이터 구조 상담부터 씬 연결·튜토리얼 구현까지.
3. **가장 큰 효과는 코드 생성이 아니라 검증 자동화였습니다.** AI가 쓴 코드보다 AI가 쓴 *검증 도구*가 더 많습니다(1,331줄 대 1,057줄). 이 이야기가 4장이고, 이 보고서의 중심입니다.

## 1. AI를 넣지 않기로 한 결정

이 게임의 마지막 관문은 '사건 판결'입니다. 플레이어가 범인을 지목하고 사건의 전말(동기·대상·수단·목적)을 서술하면 유죄/무죄/증거 불충분이 갈립니다.

여기는 LLM을 넣기 좋은 자리였습니다. 플레이어가 자유 문장으로 사건을 서술하면 모델이 정답과 대조해 채점하는 방식이 자연스럽게 떠오릅니다. **검토했고, 쓰지 않기로 했습니다.**

**대신 채택한 방식** — 빈칸 채우기(구조화 입력) + 표면 유사도 매칭

```
{범인}은(는) {동기} 때문에 {대상}을(를) 노려 {수단}(으)로
국가 DB를 침입해, 전산망을 {목적}시키려 했다.
```

각 빈칸은 독립적으로 판정됩니다. 오타와 동의어는 `StringSimilarity`가 흡수합니다 — 한글을 초성/중성/종성으로 분해한 뒤 Levenshtein 편집거리를 재는 방식이라, "해킹"과 "해킹"의 오타뿐 아니라 자모 하나가 틀린 입력까지 잡아냅니다.

**그렇게 한 이유**

| 기준 | 자유 문장 + LLM 판정 | 빈칸 + 편집거리 (채택) |
|---|---|---|
| 같은 입력, 같은 결과 | 보장 안 됨 | 항상 동일 |
| 판정 근거 설명 | 어려움 | 필드별로 O/X와 정답을 그대로 제시 |
| 네트워크·비용·지연 | 매 판정마다 발생 | 없음 |
| WebGL 배포 | API 키 노출·CORS 문제 | 순수 C#, 외부 의존성 0 |
| 파싱 예외 | 문장 해석 실패 가능 | 구조상 발생하지 않음 |

추리 게임에서 판정의 일관성은 재미의 전제 조건입니다. 같은 답을 넣었는데 어제는 맞고 오늘은 틀리면 플레이어는 추리를 멈춥니다. 짧은 데모에서 확률적 판정이 주는 위험이 이득보다 컸습니다.

> **기록해 둘 점** — "AI를 쓸 수 있는 자리에 쓰지 않은 것"도 이 프로젝트의 AI 관련 의사결정입니다. 도입 여부를 따져보고 근거를 남긴 뒤 내린 결론입니다.

## 2. 설계 상담

초기 데이터 구조 설계 단계에서 AI에게 아키텍처를 상담했고, 그 결과가 코드에 그대로 남아 있습니다.

핵심은 **authored 데이터와 런타임 상태의 분리**입니다. 질문·증언·용의자 같은 '작성된 데이터'(`QuestionNode`, `Testimony`, `SuspectData`)는 순수 데이터로 두고, "무엇을 물어봤는가 / 어떤 증언을 확보했는가" 같은 진행 상태는 `CaseProgress`가 따로 관리합니다.

```csharp
// 사건 진행 중의 '런타임 상태'만 담는다 (authored 데이터와 철저히 분리 — GPT 조언의 CaseState).
public class CaseProgress { ... }
```

이 분리 덕분에 얻은 것:

- 사건 데이터를 ScriptableObject로 빼서 기획자가 인스펙터에서 편집 가능
- 사건을 다시 시작할 때 `CaseProgress`만 새로 만들면 초기화 완료 — 실제로 4장의 루프 검증에서 재플레이 시 상태 누수가 없음이 확인됐습니다
- 질문 흐름이 트리가 아니라 **방향 비순환 그래프(DAG)** 라서, "A의 진술과 B의 진술을 둘 다 확보해야 열리는 모순 질문"이 자연스럽게 표현됨

> 📝 **팀 작성 필요** — 이 장은 코드에 남은 흔적으로만 재구성한 것입니다. 실제로 어떤 모델에 무엇을 물었고 어떤 대안을 검토했는지는 상담을 진행한 팀원이 보강해 주세요. (예: 사용 모델, 상담 시점, 채택하지 않은 대안 구조)

## 3. 에이전트형 개발

후반 작업은 **Claude Code**(에이전트형 코딩 도구)로 진행했습니다. 특징은 사람이 코드를 받아 적는 게 아니라, AI가 직접 저장소를 읽고 파일을 고치고 Unity를 실행해 결과를 확인한다는 점입니다.

이 방식에서 실제로 나온 결과 세 가지를 적습니다.

### 3.1 씬 연결 — 코드가 아니라 '끊긴 곳'을 먼저 찾았다

Start / CaseSelect / Main / EndingScene 네 씬을 잇는 작업이었는데, 구현 전에 **실제로 끊겨 있던 결함 세 개**가 먼저 나왔습니다.

| 결함 | 증상 |
|---|---|
| `Start.unity`의 START·How To Play 버튼에 `onClick` 핸들러가 하나도 없음 | 눌러도 아무 일도 일어나지 않음 |
| `InterrogationController`가 `GameSession.SelectedCase`를 읽지 않음 | 어떤 사건을 골라도 인스펙터 기본 사건만 실행됨 |
| 빌드 첫 씬이 빈 `SampleScene` | 빌드하면 아무것도 없는 화면에서 시작 |

두 번째가 특히 중요했습니다. 사건 선택 화면은 고른 사건을 `GameSession`에 정확히 넣고 있었지만 받는 쪽이 무시하고 있었습니다. 양쪽 코드를 따로 보면 둘 다 정상으로 보이고, **연결 지점을 봐야만 드러나는** 종류의 결함입니다.

### 3.2 판정 순서 버그 — 정답을 다 맞혀도 오답이 되던 문제

작업 중 발견한 잠재 버그입니다.

빈칸의 **배치 순서**는 문장 템플릿(`verdictTemplate`)이 정하고, **채점 순서**는 사건 데이터(`verdictFields`)가 정합니다. 그런데 판결 화면이 입력값을 순서만 있는 문자열 목록으로 넘기는 순간 "어느 빈칸이 어느 항목의 답인지"가 사라졌고, 채점기는 그것을 위치로 짝지었습니다.

당시 두 사건은 문장 순서와 항목 선언 순서가 우연히 같아서 증상이 없었습니다. **기획자가 문장에서 빈칸 순서만 바꾸면 그날부터 모든 정답이 오답이 되는** 상태였습니다.

실제로 재현했습니다. 같은 사건에서 문장의 빈칸 순서만 뒤집고 네 칸 모두 정답을 넣었을 때:

| | 결과 |
|---|---|
| 수정 전 | **0 / 4 · 증거 불충분** |
| 수정 후 | **4 / 4 · 유죄** |

수정은 값만 넘기는 통로 자체를 없애는 방향으로 했습니다. 판정기가 `(항목, 입력값)` 짝을 받아 내부에서 정렬하므로, 호출부가 순서를 틀릴 방법이 사라졌습니다. 회귀 테스트 7건을 함께 남겼습니다.

### 3.3 인터랙티브 튜토리얼 — 대본을 데이터에서 뽑아냈다

이 게임에서 플레이어가 스스로 알아낼 수 없는 규칙은 하나입니다.

> 기록지에서 **증언 두 개를 고르면** 게임이 모순을 판정하고, 성립하면 그 진술의 주인에게 즉시 추궁이 들어간다.

그래서 튜토리얼은 이것 하나를 플레이어 손으로 성립시키게 만드는 데 집중했습니다.

설계 단계에서 사건 데이터를 먼저 분석했더니 결정적인 사실이 나왔습니다 — **모순 두 개가 전부 서로 다른 용의자의 진술을 요구**합니다. 한 사람만 취조해서는 모순을 만들 수 없습니다. 제약처럼 보이지만 오히려 선물이었습니다. 가르쳐야 할 교훈("한 명만 파면 안 된다")이 데이터에 이미 박혀 있었으니까요.

그래서 튜토리얼 대본을 하드코딩하지 않고 **그래프에서 도출**하도록 만들었습니다(`TutorialPlan`).

```
1) 모순 질문 하나를 고른다 (필요 증언 2개짜리)
2) 그 두 증언을 선행 조건 없이 바로 얻을 수 있는 질문을 찾는다
3) 그 질문들의 주인 = 튜토리얼이 부를 용의자
```

결과적으로 사건을 새로 만들어도 튜토리얼이 따라옵니다. 실제로 세 사건 모두에서 경로가 자동으로 나옵니다.

```
TutorialCase              박 주임 + 이 사원 → TUT_A_CONTRA
SampleInterrogationCase   클로버  + 렉스    → A_C_LEAVE
SampleInterrogationCase2  클로버  + 리나    → A_C_LEAVE
```

화면 처리는 셰이더 없이 해결했습니다. 하이라이트할 버튼의 사각형만 남기고 **상·하·좌·우 네 장의 딤 패널**로 화면을 덮으면, 이 패널들이 레이캐스트를 먹기 때문에 "지금 눌러야 할 것 외에는 눌리지 않는" 효과가 공짜로 따라옵니다.

## 4. 검증 자동화 — 이 프로젝트에서 AI가 가장 크게 기여한 부분

에이전트형 개발에는 구조적인 문제가 있습니다. **AI는 Unity 에디터를 눈으로 볼 수 없습니다.** 씬을 열어 버튼을 눌러보는 것을 사람이 대신 해줘야 한다면, AI가 코드를 빨리 쓰는 이점이 검증 병목에서 전부 사라집니다.

그래서 AI가 자기 결과물을 스스로 확인할 수단을 먼저 만들었습니다. Unity를 `-batchmode -nographics`로 띄우고, **헤드리스 플레이모드에서 실제로 버튼을 눌러 게임을 진행시키는** 하니스입니다.

| 하니스 | 하는 일 | 줄 수 |
|---|---|---|
| `SceneFlowValidator` | 씬을 열어 전환 대상이 빌드 설정에 있는지, 루프가 닫히는지 정적 확인 | 377 |
| `SceneFlowPlaythrough` | 타이틀→사건선택→취조→엔딩→복귀를 **두 바퀴** 실제로 클릭해 진행 | 380 |
| `TutorialPlaythrough` | 튜토리얼 16비트를 하나씩 밟고 타이틀 복귀까지 확인 | 334 |
| `VerdictEvaluatorTests` | 판정 로직 회귀 테스트 7건 | 240 |
| **합계** | | **1,331** |

같은 기간에 만든 **기능 코드는 1,057줄**입니다. 검증 도구가 기능 코드보다 많습니다(전체 신규 코드 2,388줄 중 **56%**).

처음에는 과해 보였지만, 실제로 값을 했습니다.

### 하니스가 잡아낸 것들

**AI가 잘못 짠 튜토리얼 동선** — 처음에는 "취조 종료 → 다른 용의자 호출"로 안내하도록 만들었습니다. 검증을 돌리자 6번 비트에서 멈췄습니다. `DialogueManager`가 **질문이 남아 있는 동안 취조 종료 버튼을 숨기고** 있었기 때문입니다. 사람이 직접 플레이했다면 "왜 버튼이 없지?" 하고 한참 헤맸을 지점입니다. 전화기로는 언제든 상대를 바꿀 수 있으므로 그 경로로 수정했습니다.

**AI가 잘못 판단한 것** — 작업 중 "기록지에 다른 이름이 표시된다"고 보고했으나, 코드를 더 확인해 보니 **사실이 아니었습니다.** 기록지 제목은 용의자 데이터에서 이름을 가져오고 있었고, 문제의 필드는 런타임에 읽히지 않는 값이었습니다. 잘못된 진단을 근거로 작업을 진행하기 전에 정정했습니다.

**AI가 처음 쓴 코드의 결함** — 튜토리얼 오버레이 초안에는 두 개의 명백한 버그가 있었습니다. 전화기 재호출 조건이 매 프레임 플래그를 초기화해 **영원히 성립할 수 없는 상태**였고, 종료 처리가 `Destroy(gameObject)`를 호출해 **같은 오브젝트에 붙어 있던 게임 컨트롤러까지 파괴**할 참이었습니다. 둘 다 실행 전에 잡았습니다.

**엔지니어링 장애도 있었습니다** — 배치모드에서 플레이모드로 진입하면 도메인 리로드가 에디터 루프를 멈춰 세워 프로세스가 무한 대기에 빠졌습니다. 진입 시 도메인 리로드를 끄고 끝나면 원래 설정으로 되돌리는 방식으로 해결했습니다.

### 안전장치

검증은 **팀원이 열어 둔 Unity 에디터를 건드리지 않도록** 프로젝트 사본을 따로 만들어 그곳에서 실행하고, 끝나면 사본을 삭제했습니다. 원본 프로젝트와 에디터 세션은 검증 과정에서 한 번도 영향을 받지 않았습니다.

### 최종 검증 결과

```
씬 흐름 정적 검증      통과 (0개 경고)
실제 게임 루프 2바퀴    통과  (유죄 경로 · 오인 지목 경로 모두)
튜토리얼 전 구간        통과  (16비트 → 모순 성립 → 타이틀 복귀)
판정 회귀 테스트        통과 (7/7)
컴파일 오류             0건
```

## 6. 정리

**잘 통한 것**

- 검증 수단을 먼저 만든 것. AI에게 "돌려보고 결과를 가져오라"고 시킬 수 있게 되자 반복 속도가 완전히 달라졌습니다.
- 대본·경로를 하드코딩하지 않고 데이터에서 도출하게 한 것. 사건을 추가해도 튜토리얼이 따라옵니다.
- AI에게 코드를 짜라고 시키기 전에 **먼저 데이터를 분석하게 한 것.** 모순이 전부 용의자 사이에만 존재한다는 사실을 먼저 알아낸 덕분에 튜토리얼 설계가 통째로 정해졌습니다.

**주의해야 했던 것**

- AI의 진단을 그대로 믿으면 안 됩니다. 실제로 한 번 틀린 원인 분석을 내놓았고, 코드를 더 읽어서 정정했습니다.
- AI가 처음 쓴 코드에는 실행하면 바로 드러날 결함이 있었습니다. 자동 검증이 없었다면 사람이 플레이하다 발견했을 것입니다.
- 게임 로직처럼 **눈으로 확인해야 하는 영역**은 AI 단독으로 완결되지 않습니다. 검증 자동화가 그 간극을 메우는 수단이었습니다.

**남은 것**

- 튜토리얼의 딤 처리는 현재 정답 버튼 외 모든 클릭을 막습니다. 확실하지만 답답할 수 있어, 시각 효과만 남기고 클릭은 열어두는 선택지도 검토 중입니다.
